# 부록

설계 문서의 결정 근거와 확장 계획이다.

## 확장안

| 항목 | 다시 도입할 조건 |
| --- | --- |
| 메모리 캐시(인기 대출·ISBN·소장) | 첫 주 실측 응답 시간이 목표를 넘을 때 |
| 배치 + 후보 목록 DB | 정보나루 일 한도의 50%를 넘거나 첫 요청 지연이 문제일 때 |
| Redis 등 공유 캐시 | 서버가 2대 이상일 때 |
| 후보 확대 + 벡터 저장(pgvector) | 인기 대출 밖의 책까지 후보를 수백 권 이상으로 늘릴 때(예스24 소개문 임베딩 저장은 1:1 문의 필요) |
| NLK 쪽수 보완·'사서 추천' 표시 | 예스24 쪽수 빈 비율이 15%를 넘을 때(키 발급 승인 필요) |
| 예스24 제휴 링크 | 구매 클릭이 측정될 만큼 생길 때(해제 불가 정산 조건, 제휴 키 유료화 예정) |
| 호출량 계측·경보 | 일 한도의 30%에 가까워질 때 |
| 평점·판매지수 정렬 | 임베딩 장애 때 대출순 말고 다른 정렬이 필요할 때 |
| 위기 대응(위험 문구 감지, 109 안내) | 출시 전 안전·법무 검토에서 요구되거나, 보관된 고민에서 위험 문구가 확인될 때 |

## 추천 방식 비교(약관 관점)

예스24 약관은 일시 저장은 허용하고 별도 DB 구축은 금지한다(Open API 탭 > 약관 검토). 세 방식 모두 예스24 데이터를 DB에 쌓지 않는다.

| 항목 | A. 실시간 + 캐싱 | B. 인메모리 RAG(채택) | C. LLM 판단 |
| --- | --- | --- | --- |
| 방식 | 예스24 응답을 ISBN 단위로 짧게 캐시. 순위는 B·C와 조합 | 고민과 소개를 요청 때 임베딩해 유사도로 순위, LLM은 이유만 | 고민과 후보를 LLM에 한 번에 주고 N권·이유를 받음 |
| 약관 | 기한 있는 일시 저장은 허용, 배치로 미리 채우면 위반 소지 | 문제 없음(벡터를 DB에 저장하면 1:1 문의 필요) | 문제 없음 |
| 추가 구성·호출 | 캐시 | 임베딩 API, 호출 2회 | 없음, LLM 1회 |
| 품질 | 순위 방식에 따름 | 같은 입력이면 같은 순위, 상황과 내용의 표현 차이에 약함 | 맥락 이해가 가장 좋을 가능성, 결과가 조금씩 다를 수 있음 |

결론: 회의에서 B로 정했다(2026-11-26). 같은 입력이면 같은 순위가 나오고, LLM은 3권의 이유만 쓰므로 입력이 짧다. 고민(상황)과 소개(내용)의 표현 차이에 약한 점은 평가 세트로 확인하고, 부족하면 C나 LLM 재순위로 보완한다. A는 메모리 캐시와 함께 실측 후 정한다.
